# claude-lead 设计笔记

这份笔记解释 `SKILL.md` 里每条规则从哪来。规则都是从一个月左右的真实派发台账里复盘出来的，下面只保留结论和依据的形状，
具体事例、会话 id、业务名都去掉了。你在自己的环境里跑一段时间后，数字会不一样，但大概率会碰到同样的几类问题。

## 1. 为什么要分「主管」和「执行者」

- 主会话的开销大头不是输出，是**缓存读**：上下文越大、轮数越多越贵。统计过几个「主会话自己从头做到尾」的实现会话，
  缓存读占等效开销约 80%。委派省钱的机制是把读文件、调试的轮次移出主会话，而不是少写几行代码。
- 按工作类型拆开看，读代码约 40%、只读查询约 15%、构建测试和端到端约 20%，改文件只有个位数。所以真正该外移的是「看清楚」，
  不只是「写代码」。
- 由此定下分工：**执行者负责看清楚，主管负责想清楚；实现只在想清楚之后才派。**

## 2. 触发：按「做什么」触发，而不是按「工作量」触发

- 早期技能写的是「工作量大就派」。结果几乎不触发：模型是逐步决策的，事先估不出工作量；「上下文超过 N」它也感知不到。
- 稳定触发的是按**任务类型**写的描述（排查、盘点、读长方案、对比分支、跨模块找调用方）和**时机**（接到任务时、方案拍板那一刻、
  讨论方案开头）。所以技能描述里写的是这三个时机，而不是阈值。
- 还剩一类漏派：请求的字面更贴某个专项技能（比如「排查下这个问题」更像一个排查技能），模型只加载那个技能，委派判断根本没被读到。
  一开始的修法是在每个专项技能里都写一遍派发分支，很快变成强依赖。最终的做法是：
  - 派发判断只在**全局约定**写一处（见仓库 `global/AGENTS.example.md`），专项技能只写怎么做、不点名执行方；
  - 用 hook 兜底：主会话连续 N 次只读调用就注入一次提醒（`hooks/posttool_delegate_nudge.py`），提醒只指向全局约定。
- 阈值怎么定：用 `scripts/timing.py` 回放历史会话，看不同阈值能覆盖多少「≥60 次调用却没派」的会话、会多触发多少次。
  当时 25 次覆盖了 26/27，30 次覆盖 24/27；侦察派早了没有观察到返工代价，于是取 25。

## 3. 契约：大多数返工是契约的锅，不是执行者的锅

台账里每次非通过都标 `cause`（brief / env / capability / right_stop）。几轮下来，施工返工的原因压倒性地是 **brief**。细分后：

| 缺口 | 典型表现 | 对策 |
|---|---|---|
| 范围画窄（scope） | 只改了契约点名的文件，漏了同一行为的其他入口、组合根接线、生成物、另一端校验；最贵，常常跑完整轮才发现 | 模板从「允许改：文件清单」改成「行为范围」：写行为 + 起点，其他入口默认在范围内 |
| 口径未定（undecided） | 遇到取舍停下 | 便宜，停下是对的；派前先列「未决口径」，能问的先问 |
| 事实写错（fact） | 迁移编号凭印象猜错、要求更新不存在的文件、契约里的工作区状态已过期 | 机械事实交给执行者「现场自决」；工作区快照由 dispatch 在派发瞬间自动采集 |
| 外部行为不清（external） | 离线测试全过，真实调用一跑就出问题 | 涉及外部系统的验收必须含一条真实冒烟 |
| 约束冲突（conflict） | 两条约束互相打架，执行者只能停 | dispatch 拒收和固定约束冲突的 brief（例如指定写 /tmp） |

另外两条来自「执行者按字面执行」这个特性：

- 写进**硬不变量**的东西它不会质疑。有一次把一条没核实的环境规则写成了硬不变量，结果错得很整齐。所以没经侦察或用户拍板的规则
  一律写成**待核假设**，让它先对照同模块现有接口核实。
- 施工前让它**先查契约缺口**：对照同类接口列出契约没提的规则，影响验收的停下，其余按现有做法补上并在汇报里列出。
  复核时先读这一栏，补得对就接受，太离谱说明它在乱补。

## 4. 侦察的停止条件要写到「要回答的层级」

「找到证据即停」会诱导早收尾：执行者看到一条直接报错就交差，没追到具体缺什么。另一个极端是「尽量往前搜、至少 14 天」，
它会按字面翻满。停止条件写成要回答的问题本身，范围交给它判断。

## 5. 不能派的两类

- **状态正在变**：用户正在授权、改配置。派出去的执行者拿到的是旧状态，查完的结论我同时段已经自己核实过一遍，等于付两次钱。
- **决定性验证是一次只有我能做的写操作**。

用户点名派这类任务时，先一句话提议拆分或自己做。

## 6. 脚本层面踩过的坑

都已在 `scripts/dispatch.sh` 里处理，换执行者时值得逐条检查：

- 派发后又改 brief：dispatch 已经拷走旧版。→ brief 拷进 run 目录，以 run 目录里的为准。
- 用前台 `&` 启动再自写 `while pgrep -f <run目录>` 等待：`pgrep -f` 匹配到等待脚本自己，空等一小时。→ 一律后台调用、等通知。
- 派发运行中改了 dispatch.sh 本身，bash 边读边执行导致崩溃、没记账。→ 整个脚本包在 `main` 函数里。
- 续派时把 run 目录当会话 id 传，执行者静默开了新会话，上下文全丢。→ `RESUME` 同时接受 task_id 和 run 目录，校验会话 id 格式，没接上原会话就告警。
- `codex exec resume` 不接受 `-s / -C / --add-dir`，也不沿用首派的放行。→ resume 时用 `-c sandbox_mode` + `writable_roots` 显式给。
- 沙箱只读家目录：CLI 登录态刷新回写失败、git worktree 的 gitdir 在主仓 `.git/worktrees/` 下写不了 index.lock、
  fnm 的 node 软链目录只读。→ 按需放行（`DELEGATE_WRITABLE`），只放本 worktree 自己的 gitdir，不放整个主仓 `.git`。
- 模型容量报错很快退出、无产出。→ 自动重试一次。
- 执行者把中间产物写到 /tmp，复核时漏看。→ 固定写 run 目录，brief 指定 /tmp 写入会被拒收。

## 7. 记账口径

- **按任务聚合**，不按派发轮次：返工沿用原 task_id（`RESUME` 或 `TASK=`），否则一个需求返工三次会被记成三个「一次通过」。
- 一次通过 = 只派一轮、pass、复核后没手修。复核后自己补改过要老实记 `--hand-fixed`。
- 冒烟任务（标签以 smoke 开头）不进效率统计。
- 主会话和执行者的 **token 比例**只看工作量分布，不看钱（单价不同）。比例长期很低说明工作量没真的移出去，回到「漏派」找原因。

## 8. 对照过、但没采用的模式

- 严格的「主管只规划、不碰代码」：返工瓶颈在契约，不在执行；完全不下场只会让契约更差，小修冷启动也不划算。
  采用的是反过来的默认值——施工默认派，例外只有三种。
- 派完由脚本自动重跑验收再续派：执行者已经跑过验收，重复跑测试。
- 多执行者路由：执行者只有一个时，路由没有意义；默认双路侦察只在高风险根因排查时临时用。
- 返工时自动升推理档（级联回退）：只对 `cause=capability` 的返工有意义，先攒数据。
