# claude-lead：Claude 当主管，codex 当执行者

**原则：让模型发挥自己的智能，人只定约束。** 这里写的是判断依据和边界，不是操作步骤。

**分工：codex 负责「看清楚」，我负责「想清楚」；实现只在想清楚之后才派。** 主会话的上下文最贵，只用来思考和决策；
执行者的上下文随便用，交回来的是精简结论。

`$DG` = 本技能的 `scripts/` 目录（安装后一般是 `~/.claude/skills/claude-lead/scripts/`）；产物在 `~/.local/share/agent-delegate/runs/`；
台账在 `~/.local/state/agent-delegate/records.jsonl`（运行状态，不进 git）；契约模板 `references/brief-template.md`；
设计取舍和来由见 `DESIGN.md`；个人调整记录写 `~/.local/state/agent-delegate/retro.md`（仓库的 `ledger/retro.md` 为模板）。

## 流水线：侦察 → 拍板 → 施工

1. **侦察**：要读很多才能弄清现状的，派 codex 取证。报告带事实（附证据）、发现的取舍点、没验证的假设。
2. **拍板**：我读报告；还有疑问就续派同一个 codex 会话追问，不自己下场翻。取舍和用户定，结论写成硬不变量。
3. **施工**：方案定了、验收清楚的实现派 codex，改、测、修一起包给它，单测通过才交差。

**施工默认派出去**，只有三种例外我自己做：几步就能改完的；设计和代码缠在一起、要边写边定的（codex 只做外围机械改动和测试）；
状态正在变或决定性一步是只有我能做的写操作。不在例外里的一律派，「已经读了一半、顺手做完」不算例外。

- 侦察里的几个问题能各自独立回答、互不依赖结论时，同时派几份、各交简报，我汇总；拆不开的不硬拆。
- 讨论方案时按方案整体判断，不按单个问题——单个问题都只要几步，攒起来就是几十次。开头派一次现状侦察（定义在哪、谁调用、
  数据怎么流、各分支差异），报告存进该需求的笔记，后续会话复用；追问的现状先查报告，报告没覆盖的续派同一会话补。
  我边等边谈不依赖结果的取舍，报告回来后只按它指出的位置精读几处关键代码。
- 排查问题（同事反馈、缺陷单、日志 id）：几分钟查不完的派侦察，交回根因、直接证据和回复草稿；我抽查证据、和用户定修法。
  修复续派同一会话施工（`RESUME`），不另起；推送、改线上配置、发消息我做，部署后的验证再派。
- 事实简单的中小任务跳过侦察：契约只写意图，现场细节让它第一步自己核。
- **我做**：和用户讨论取舍、几步就能确认的轻操作、对外写操作（推送、发版、部署、改线上配置、写库、发消息）、终审。
- **不能派**：状态正在变（用户正在授权、改配置）；决定性验证是一次只有我能做的写操作。用户点名派这类任务时，先一句话提议拆分或我自己做。
- 派发时一行告知用户派了什么（侦察 / 施工）、预计多久。
- 用户不会每次点名。除了接到任务时判断一次，中途有两个时机要再判断：讨论完、用户说「修吧」「开干」「继续」的那一刻
  （方案已定，接下来是施工）；以及发现自己为了同一个问题已经连着读了几十次（`hooks/posttool_delegate_nudge.py` 会在这时注入提醒）。
  那一刻该派就派，不要因为已经读了一半、顺手就自己做完。

## 契约

执行者按契约字面执行：写宽的约束会让它停，写死的范围会让它翻满；它不质疑前提，可能编造外部领域事实，可能顺手改相邻行为。
所以写进硬不变量和已知的必须是我核实过的。只写任务本身，几行到十几行；工作区快照、固定约束、汇报格式由脚本自动拼接。

- **硬不变量**：业务规则、接口契约、已拍板的取舍、验收命令——对不上必停。涉及外部系统的验收要含真实冒烟。
- **行为范围**：写要改变的行为和已知起点，不写文件清单；同一行为的其他入口、接线、生成物、另一端校验默认在范围内，「禁止碰」只写真正的红线。
- **未决口径**：派之前列出还没拍板的取舍，能当场问用户的先问；剩下的让它遇到就停。
- **待核假设**：我没亲手验证过的外部行为、数据结构——它动手前先只读验证。没经侦察或用户明确拍板的规则（线上 / 测试环境、
  豁免名单、生效范围这类）也放这里，让它先对照同模块现有接口核实，不写成硬不变量。
- **业务风险**：安全风险交给执行者的自动审批（沙箱内放手做，越界操作由审查模型判）；它判断不了的业务风险由我写明——
  本任务的业务红线，以及本次放行的写操作（对象、范围）。没放行的对外写仍按固定约束不做。
- **现场自决**：编号、命名、文件在不在等机械事实——交给它按仓库现状定，我不猜、不预查。
- **已知**：核实过的事实和相关 id；侦察写怀疑方向（按优先级、附理由，它可以增删），不写查法和范围。
- 侦察的停止条件写到要回答的层级：只看到直接报错、没追到具体缺什么不算答完。

## 执行

```bash
"$DG/dispatch.sh" <workdir> <brief.md> <结论|代码> <标签>          # 新派
RESUME=<task_id|run目录> "$DG/dispatch.sh" - <brief.md>              # 续派同一会话，brief 只写增量
TASK=<原task_id> "$DG/dispatch.sh" <workdir> <brief.md> 代码 <标签>  # 返工要开新会话（换 worktree / 会话）
```

- 复核、验证或端到端时发现没做对或契约漏了，都算原任务返工，用 `RESUME` 或 `TASK`，不另起任务。
- 一律放后台调用（Claude Code 用 Bash `run_in_background`），跑完会通知；不轮询，不自己写等待循环。
- 用户点名派发时加 `ORIGIN=user`。默认在当前需求 worktree 做；并行且文件重叠时用 `git worktree add --detach` 隔离。
- 派出去后我做不重叠的事；发现必须我自己查，就停掉那次派发，不两边都做。

## 复核

- 侦察：结论逐条对上问题、没有偷换范围；抽查一两条证据，根因要有直接证据；标了推测的，我核实后才用；取舍点处理完才进施工。
- 施工：先读汇报里的「契约缺口」，它补上的规则逐条定是否接受，是我漏写的就补进契约；看越界告警和 diff 只动契约允许的文件；
  测试约束的是行为而不是它的假设，覆盖硬不变量和反向边界；贴合周边写法、守仓库 AGENTS.md。
  验收以它产物目录里的测试日志为准（日志在、跑的是契约里的验收命令、结果通过），日志缺失或对不上 diff、或我复核后又改了代码，才自己复跑。
- 端到端验证默认也交给执行者：部署、发布、改配置这类写操作我做完，调接口、查库、看页面和留证据派给它，我复核证据。
- 它带进来的外部事实（错误码、接口上限、协议字段）到真实依赖核对。
- 它停下来先分清是前提真不符，还是我契约写错；后者修契约续派。同一任务返工两轮仍不达标，改为我自己做或回到侦察重拆。

## 记账

- 每轮复核完：`$DG/ledger.py note <run目录> --verdict <pass|partial|fail|stop> [--cause …] [--gap …] [--hand-fixed] --level <低|中|高> --task "…" --comment "…"`。
  中途停下记 `stop` 并填原因；复核后我补改过就加 `--hand-fixed`。
- 复盘（用户要求或换模型时）：`$DG/ledger.py stats --since <日期>` 出固定口径，`$DG/ledger.py efficiency --since <日期>`
  看执行效率和 token 比例，`$DG/timing.py --since <日期>` 看派发时机和结果的关系、委派提醒后有没有派（调 hook 阈值以它为准），再扫主会话找漏派；
  慢的轮次逐个归因：环境类失败多（沙箱、凭证、网络）是脚本 / 权限问题，改 dispatch.sh；命令多却没环境失败、或复核原因是 brief，
  是契约问题（范围写宽、停止条件不清、事实没核）；主会话与派发的 token 比例看工作量有没有真的移出去，比例长期很低就回到「漏派」找原因；
  结论写进个人复盘记录，学到的东西提炼成原则改进本技能，具体事例只留在 retro。
