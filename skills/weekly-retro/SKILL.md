# weekly-retro：每周复盘

\`$WR\` = 本技能目录（一般是 \`~/.claude/skills/weekly-retro/\` 或 \`~/.codex/skills/weekly-retro/\`，按实际安装目录取值）。
\`$RETRO_DIR\` = 个人复盘目录（默认 \`~/notes/retro\`，运行脚本时沿用同一个目录）。每期一个 \`<年>-W<周>/\` 子目录，跨期的 \`metrics.jsonl\`
放在 \`$RETRO_DIR\`。个人回放和台账放在 \`$RETRO_DIR/replays/\` 和 \`$RETRO_DIR/ledger/\`。仓库提供格式示例，按需复制模板到个人目录。
扫描配置可放在 \`$RETRO_DIR/config.json\`，也可通过 \`RETRO_CONFIG\` 指定文件。
方法论的来由见 `DESIGN.md`。

## 原则

- **怪环境，不怪模型。** 模型能力当常数，结论不能是「它没看懂」，要落到「那一刻缺了什么信号、多了什么噪音、哪个工具误导了它、哪里缺早期拦截」。
- **介入即失败。** 用户中途纠正 agent，或追问进度、卡顿，都说明环境有缺陷；要把那句话变成持久的环境资产。用户拍板、补需求、改范围属于正常推进，不算失败。
- **只做能产生复利的修补。** 产出物的生命周期要长于单次会话。帮某个任务过关的一次性修补不算复盘产出。
- **先看轨迹，再动手。** 没看过拐点前后的完整轨迹，不改规则、不加提示语。

## 1. 回填上期

首期没有上一期时，从最近七天开始，跳过回填。以后读上一期 `retro.md` 和 `$RETRO_DIR/ledger/changes.md` 里「待验证」的条目，用本周的证据判定为有效、无效或仍待验证：对应指标的变化、回放题是否通过、
同类问题是否再现、hook 的命中与豁免情况。判定为无效的，分析原因（没触发？写错了？归因错了？），作为本期的发现。

- 每期的会话量差别很大，跨期比较用 `metrics.json` 里的 `rates`（每千次工具调用、每百条用户消息），不比绝对数。
- 「有没有走技能」看 `skill_usage`；`--help` 类改动看 `help`：查过 `--help` 的会话里有多少加载过速查技能，以及 `top` 里哪些命令速查还没覆盖。
- 改动针对的场景本期没出现（例如没有新需求开工），记「仍待验证」，不要因为指标没变坏就记有效。
- **每两期评估一次复盘本身**：跑 `python3 -I "$WR/scripts/tune_due.py"`。输出 `DUE` 就读 `references/tune.md`，本期做完它的第 1、2 节
  （只读评估和调整方案），结果并进第 6 步的确认表；`NOT_DUE` 就跳过。用户只说「看看复盘效果怎么样」「优化下复盘技能」时，
  不跑整期复盘，直接按 `references/tune.md` 做。

## 2. 收集数据

- **范围是本机所有项目**，包括各仓库的分支、worktree 和临时目录里的会话。开始前告知用户扫描范围。报告可能包含消息原文、命令、路径和资源标识。只把归因所需的片段带入模型上下文，先遮掉凭证和与任务无关的身份信息。复盘产物留在个人目录。
- **指标**：`python3 -I "$WR/scripts/scan.py" --since <起点> --until <终点>`。窗口从上期的 `until`
  接着算（见 `metrics.jsonl` 最后一行），不要固定从周一起，否则两期之间的会话没人看；`--until` 写明，重跑才得到同样的数。
  默认按终点所在的 ISO 周在 `$RETRO_DIR` 下写报告，可用 `--out` 指定仓库外的目录。先看 `metrics.json` 的 `coverage`，确认本周用过的仓库和 worktree 都在里面。关注这几项：
  - `intervention_correction`、`intervention_observability`：用户纠正、追问进度或卡顿；
  - `empty_confirm`：agent 停下来问、用户只回一句「提交吧」「好的」。多了说明它在不该停的地方停；
  - `self_correction`；
  - `help_lookup`、`denied`、`tool_error`（细分见 `error_kinds`）；
  - `flows`：高频高成本流程，不看成败。`top` 按领域给出流程实例数、会话数、平均 / 最大步数、耗时、`--help` 次数和专用工具采用率
    `tool_share`；`repeated_entities` 是跨 3 个以上会话反复手写的 ID / 坐标；`adhoc_wrappers` 是临时手写的接口包装脚本。
    领域表在 `config.json` 的 `domains`，表外的命令按「程序 子命令」自动成族；表外的族连续两期排进前列，就补进 `domains`（有专用工具的写上工具正则）；
  - `hook_hits`：各规则的命中次数和豁免次数。已安装 Hook 时，扫描前先用 Bash 工具逐条跑守卫（仓库 `hooks/pretool_guard.py`）里每条规则的
    `selftest` 命令，应当被拦，扫描里出现 `<rule>:selftest`；没被拦或没记上，先修 hook 再看命中数。自测正常、连续 3 期零真实命中的规则，提议删除。

  复盘会话（用 `/weekly-retro` 发起，或执行过扫描、回放脚本的）从发起那一刻起不计入，之前的正常开发照常统计，
  列在 `excluded_retro_sessions`（`会话@截止时间`）。
- **介入以人工判读为准**：正则只是预标注，漏得多。通读 `turns.tsv`（窗口内所有短的用户消息），把纠正、追问、空确认挑出来，
  没标签的也要看；`retro.md` 里记判读后的数。预标注漏掉的说法补进 `scan.py` 的正则。
- **其他数据源**：用了扫描脚本没覆盖的 agent（没有本地会话记录的），本期用它做过开发时才去它的界面或 API 补介入。
- **记忆体检**：检查所有记忆目录（软链的只算一次）：超长的索引行和文件、需求已收尾却还在索引里的条目、引用已失效的东西、互相矛盾或重复的条目。

## 3. 找失败点

把指标样本和会话合起来，列出本周的失败点：用户介入、自我更正、无效震荡（同一类调用反复失败或来回切换）、步数明显偏多的任务。
同一根因的多个失败点合并成一条。

**高频高成本流程也算失败点**，即使没出错、没人纠正：看 `flows.top` 里实例 ≥5 且平均步数 ≥4 的领域，再和上期 `flows` 比是否稳定。
每个候选用 `samples.md` 给的最费步的一次加 `turn.py` 看一条完整轨迹，回答三个问题：这些步骤里哪些是每次都在重复拼的；
现有工具（你的技能脚本、CLI 速查技能、仓库里的 `.agents/skills`）能不能覆盖；有工具却没被用上的（`tool_share` 低），
是入口问题（agent 看不到）还是工具本身不够用。归到动作层；入口问题归感知层。

## 4. 拐点归因

先用 `python3 -I "$WR/scripts/turn.py" '<会话标识>|<月-日 时:分>|<关键词>' ...` 批量看每次介入之前那一回合：上一条用户消息、工具调用、
agent 最后一段话。一次可以传多个，输出是截短的，多数失败点看这个就能填四问卡。

轨迹长、要逐步看才能找到拐点的（无效震荡、步数偏多的任务），再单独派出去读，只回传一张四问卡，主会话的上下文就不会因为读轨迹而膨胀。
派给谁按全局委派约定（例如 `claude-lead`）。归因要做的：

1. **定位拐点**：`turn.py` 不够时看完整轨迹，找到第一次偏离最优路径的那一步，以及开始无效震荡的位置。
2. **快照第一视角**：只看拐点那一刻 agent 窗口里实际有什么，判断属于哪种情况：
   - 缺信息：关键约束在它没读到的地方，或者输出被截断了；
   - 脏信息：大段无关输出挤掉了重要内容；
   - 假信号：失败的操作看起来像成功，或报错有误导性。
3. **填四问卡**：
   - 现象：第几步做了 A，期望是 B；
   - 归因：那一刻缺了什么、多了什么，让 A 看起来比 B 合理；
   - 下沉：如果没人提醒，哪个环境组件应该在那一刻自动把信号喂给它；
   - 验收：补丁打上后，怎么证明同样的任务不靠人就能收敛。

## 5. 分诊与选药

每条发现必须归入一个桶，再按「动态优先」选落地方式：

| 桶 | 症状 | 动态补丁（优先） | 静态补丁（做不成动态时） |
|---|---|---|---|
| 感知层 | 不知道规则、找不到入口、被噪音淹没 | 前置检查脚本一次输出关键事实；输出截断和过滤 | 入口地图、分层披露：全局约定、技能描述、状态记忆 |
| 动作层 | 工具不会用、参数总错、多步连招繁琐 | 把高频多步操作封装成一个脚本或工具；收紧参数 | 技能里的已验证写法（CLI 速查技能） |
| 反馈层 | 走错了自己不知道、报错看不懂、最后才爆雷 | PreToolUse hook 拦截（规则见仓库 `hooks/README.md`）、报错包装成「报错 + 修复提示」、前置检查 | feedback / reference 记忆 |

- hook 只有 Claude Code 执行。会影响 Codex 等其他 agent 的问题，优先做成脚本。
- 新增或修改 hook 规则前，用最近一周的全部 Bash 命令回放一遍，确认只命中该拦的。
- 记忆失修：精简、归档、合并或删除；流水账移到笔记。
- 用户自己的使用习惯（例如超长线程）只提建议，不落地。

## 6. 给用户确认

用一张表给出每条发现：四问卡摘要、所属的桶、补丁是动态还是静态、落地位置、怎么验收（指标和回放题）。**每期最多提 5 条补丁**，
按「预估收益 × 能用上的把握」综合排序：收益是每周预估省下的步数或介入次数（看连续两期是否稳定），把握看补丁挂在哪个入口
（命令执行时的 hook / 常驻的全局约定和技能描述 > 技能正文），两项都写进表里；其余发现写进 `retro.md` 的「观察」，不进确认表，
之后反复出现再升级成补丁。用户逐条采纳、修改或驳回。不要先改再问。本期到期评估了复盘本身的，评估结论和调整方案在表里单列一组
「复盘本身」，同样逐条确认后才改。

不用等确认、直接做完再汇报的只有这几类：复盘记录和指标（`retro.md`、`metrics.jsonl`、台账回填）、扫描脚本的口径修正、
记忆里的事实性错误或缺漏。hook、全局约定、技能的行为、删除或归档记忆，都要先确认。

本周用户已经自己处理掉的问题（改了约定、修了技能），列进发现并标「已处理」，记入台账等下期验证，不再重复提补丁。

## 7. 落地、写回放题、验证

- 只改个人环境：hook、脚本、技能、全局约定、记忆、复盘记录。业务代码，以及团队仓库里的 `AGENTS.md` 和 `.agents/`，只在报告里提建议。
- 落地位置：技能和 hook 放在你的技能仓库里，改完提交；全局约定改那份被链接到各 agent 的源文件；记忆删除某条之前，
  先确认没有别的记忆用 `[[...]]` 链接它。
- 每条采纳的发现，至少写一道**只读**回放题，放进 `$RETRO_DIR/replays/`（格式见本技能的 `replays/examples/`）。题面和标准结论会发送给模型，先移除凭证和无关隐私。题目要求：
  - 写清 `prompt`、一句标准结论 `expected` 和来源；
  - 钉住固定的提交或快照，不依赖会变化的实时状态；
  - 涉及线上写操作的任务，改写成「只说步骤」的问法。
- **反事实重放**：`python3 -I "$WR/scripts/replay.py" --out <本期目录> --only <相关题号>`。这会新开只读 Codex 会话作答，
  再让一次不带工具的 Codex 调用对照标准结论判分。判分只是初筛，要人工复核回答。运行或裁判出错时结果为未判定，排查后重跑。没通过就回到第 5 步重新分诊，不要只调措辞。
- 每周只重放本期改动相关的题，加上上期没通过的题，不必全量跑。因环境原因稳定失败的题加 `paused` 字段写明原因，
  `replay.py` 会跳过；环境修好后删掉字段恢复。

## 8. 记账与汇报

- `retro.md`：发现（含四问卡摘要）、改动（标明动态或静态）、回放结果、用户决定（包括被驳回的和理由）、记忆体检前后的索引大小。
- `metrics.json` 加上 `week` 字段，追加到 `metrics.jsonl`。落地了流程类补丁的，下期回填时比对应领域的平均步数和 `tool_share`。
- `$RETRO_DIR/ledger/changes.md`：每条改动一行，写明动态或静态、判断指标、回放题号，状态填「待验证」；被驳回的也记一行。
- 简短汇报：上期改动的效果、本期主要发现、落地了什么、回放通过率、需要用户自己做的事；本期评估过复盘本身的，加一句评估结论。
