# weekly-retro 设计笔记

`SKILL.md` 是「怎么做」，这里是「为什么这么做」。内容来自连续几期真实复盘的台账（`ledger/changes.md`）和对复盘本身的评估
（`ledger/tune-log.md`），去掉了具体会话、业务名和人名，只留下可迁移的结论。

## 1. 核心思路：把 agent 的错误变成环境资产

一次会话里用户纠正了 agent，那句纠正只活在那次会话里。下周换个会话，同样的错还会再犯。复盘要做的是把它**下沉**到下次那一刻
agent 一定能看到的地方：

```
用户介入 / 无效震荡 / 高成本流程
        │  scan.py 预标注 + 人工判读
        ▼
   拐点（第一次偏离最优路径的那一步）
        │  turn.py 看那一回合，四问卡
        ▼
   分诊：感知层 / 动作层 / 反馈层
        │  动态优先：hook、前置检查脚本、封装工具 > 文档、记忆、约定
        ▼
   用户逐条确认 → 落地 → 写只读回放题
        │  replay.py：全新无头会话、不给提示，看能否自己做对
        ▼
   台账「待验证」→ 下期用指标和回放回填 有效 / 无效
```

四条原则互相支撑：

- **怪环境，不怪模型**：结论写成「它没看懂」就无处落地；写成「那一刻缺了哪个信号」才知道补丁挂在哪。
- **介入即失败**：只有用户的纠正和追问算失败，拍板、补需求、改范围是正常推进。这样指标不会因为用户多说话而变坏。
- **只做有复利的修补**：帮这一次过关的修补不算产出。
- **先看轨迹再动手**：没看过拐点那一刻 agent 窗口里有什么，就不知道是缺信息、脏信息还是假信号。

## 2. 为什么「动态补丁优先」

同一个问题，写进文档 / 记忆的静态补丁要靠 agent 在对的时刻想起来去读；hook 在命令执行时拦下、前置检查脚本一次吐出关键事实、
把多步连招封装成一个工具，不依赖 agent 想起来。所以确认表按「能用上的把握」排序时，入口位置的权重是：

命令执行时的 hook ≈ 常驻上下文（全局约定、技能描述） > 技能正文 > 记忆

评估复盘本身时专门看**动静比**：连续几期以静态补丁为主，说明复盘在偷懒，或者分诊不够深。

## 3. 指标口径踩过的坑

每个坑都对应 `scan.py` 里的一条处理，`METRICS_VERSION` 每改一次口径加 1：

- **按文件修改时间筛窗口**会把跨周长会话的上周内容算进来。→ 按每条记录的时间戳筛。
- **复盘会话会重复计数**：复盘时引用的例子被当成本期的自我更正，有一期半数自我更正来自上期的复盘会话。→ 从发起复盘那一刻截断，之前的正常开发照常算。
- **介入正则漏得多**：正则只标出 1 条纠正，人工读出 10 条。→ 正则降级为预标注，另出 `turns.tsv` 让人通读判读；漏掉的说法补进正则。
- **「被拦」误报**：把任意输出里出现 denied / not allowed 的都算，结果一期几十条全是误报。→ 只认明确的拒绝文本。
- **样本被单个会话占满**。→ 按会话轮流取样本。
- **`git grep -h` 被算成查 help**。→ help 正则只列你真正关心的 CLI（`config.json` 的 `help_clis`）。
- **长消息不是人写的**：300 字以上的「用户消息」多是 agent 写给子会话的任务说明。→ 不计介入。
- **跨期比较绝对数会失真**：每期会话量差好几倍。→ 一律比 `rates`（每千次工具调用、每百条用户消息）。
- **窗口固定从周一起**会让两期之间的会话没人看。→ 窗口接上期的 `until`。

## 4. 只看失败会漏掉「没出错但每次都很费劲」的流程

用户指出过一个漏报：「拉群消息 → 排查 → 回复」每次 4~17 步，从没出错也没人纠正，复盘就看不见。原因是扫描只按单条命令计数、
只看失败和纠正；同一个流程跨多个 CLI、被用户下一句话切成两段、`"$S" send` 这种变量写法也认不出。

于是加了 `flows`：会话按用户消息切成任务段 → 每条命令归到「领域」→ 相邻任务段（隔 ≤3 段、<60 分钟）都用到该领域就合并成一个流程实例
→ 按「实例数 × 平均步数」排序，附耗时、`--help` 次数、专用工具采用率 `tool_share`、跨会话反复手写的 ID。

已知局限：按工具不按目标（跨领域的做法测不出）；只看命令不看 Read；成本只有步数和粗略耗时。

## 5. 回放集：用「不给提示的新会话」验收补丁

- **判分不能用正则**：正则在否定句里误判（「尚未全部进入」命中「全部进入」）。→ 写一句标准结论 `expected`，用一次不带工具的模型调用当裁判；
  正则只用于 `must_not_contain`。裁判只是初筛，要人工复核。
- **题目要钉住固定的提交或快照**：问实时分支状态，分支一有新提交标准答案就失效。
- **写操作改成「只说步骤」的问法**，回放永远只读。
- **环境原因稳定失败的题**（例如无头会话取不到凭证）加 `paused`，先修环境再恢复，不要让它一直拉低通过率。
- **`codex exec` 在非终端 stdin 下会等输入**，后台跑全部超时。→ `stdin=DEVNULL`。
- 也用回放验证「删东西」：曾经想删掉全局约定里看似重复的半句，回放一跑就失败了，于是撤回。回放不只验证加的补丁，也保护删减。

## 6. 复盘本身也要被复盘

`references/tune.md` 每两期跑一次（`tune_due.py` 判断），看几个信号：

- 介入率没降 → 改动没打中真正的拐点；
- 台账大量「一直待验证」→ 验收方式不可测；
- 采纳率低 → 归因偏了或建议超出需要。有一期提了 7 条只采纳 1 条，于是加了「每期最多 N 条补丁，其余进观察」；
  后来发现上限 3 挤掉了高频流程类的发现，又放到 5，改成按「预估收益 × 能用上的把握」排序；
- hook 连续零命中 → 不知道是没场景还是 hook 坏了。→ 每条规则带 `selftest` 命令，每期先跑一次确认 hook 活着；
  自测正常、连续 3 期零真实命中才提议删除。

能删就删：长期为 0 的指标、没人看的步骤、零命中的 hook、长期 100% 通过的回放题。技能保持简短，只写判断依据和边界，具体事例留在台账。

## 7. 边界

- 只改个人环境（hook、脚本、技能、全局约定、记忆、复盘记录）；业务代码和团队仓库里的 agent 配置只提建议。
- 不用等确认就能做的只有记账、扫描口径修正、记忆里的事实性错误；行为类改动一律先给用户看确认表。
- 用户自己的使用习惯（比如超长线程）只提建议，不落地。
- hook 只有 Claude Code 执行；会影响其他 agent 的问题优先做成脚本。
