# 评估复盘本身

什么时候做：weekly-retro 第 1 步跑 `scripts/tune_due.py` 显示到期时（每两期一次）自动做第 1、2 节；用户说「看看复盘效果怎么样」
「优化下复盘技能」时不管到没到期都做。第 3 节的改动一律等用户确认。

输入：`$RETRO_DIR` 下各期的 `retro.md`、`replays/summary.json` 和 `metrics.jsonl`；`$RETRO_DIR/ledger/` 下的 `changes.md`、`tune-log.md`；
还有 hook 命中日志 `~/.local/state/agent-hooks/hits.jsonl`。

改的对象：本技能的 `SKILL.md`、本文件、`scripts/scan.py`、`scripts/replay.py`、`config.json`，个人回放集和台账（`$RETRO_DIR/replays/`、`$RETRO_DIR/ledger/`），
以及仓库 `hooks/` 里的规则。

## 1. 评估复盘效果（只读，到期自动做）

每个结论都要有台账、指标或会话里的证据：

| 角度 | 看什么 | 说明复盘有问题的信号 |
|---|---|---|
| 介入有没有减少 | `intervention_correction` 和 `intervention_observability` 的趋势，按会话数归一化 | 持平或上升，说明改动没打中真正的拐点 |
| 改动有没有用 | `changes.md` 里有效 / 无效 / 一直待验证的比例；回放通过率 | 无效多；同一问题连续几期出现；一直待验证（验收方式不可测） |
| 动静比 | 动态补丁（hook、脚本、工具）和静态补丁（文档、记忆、约定）各占多少 | 连续几期以静态为主：复盘在偷懒，或者分诊不够深 |
| hook 质量 | 每条规则的命中次数、豁免比例（≈误拦率）、连续零命中的周数、自测是否通过 | 误拦高要改匹配；自测正常但连续 3 期零命中要删 |
| 采纳率 | 被驳回的建议和理由 | 驳回多，说明归因偏了，或建议超出了用户的需要 |
| 漏报 | 用户在复盘之外自己提出的改进；复盘后仍反复出现、却没被列为发现的问题 | 扫描规则或数据源没覆盖到；拐点没看轨迹 |
| 成本 | 复盘会话的 token、子 agent 数、回放题数和耗时 | 成本涨了，介入却没降 |

另外检查：
- **指标口径是否失真**：抽查 `samples.md`，看有没有误报（比如任务说明被当成介入）、漏报。
- **回放题是否还有区分度**：长期 100% 通过的题，可以降频或退役；判分太松或太严的，要修正；因环境原因（例如无头会话取不到凭证）
  稳定失败的题，加 `paused` 停跑，先修环境再用。
- **数据源覆盖**：有没有新的 agent 或 provider 的记录没扫到。

## 2. 提出调整

每个调整对应评估里的一个具体问题，不为假设的需要加东西。能删就删：长期为 0 的指标、没人看的步骤、零命中的 hook、没有区分度的回放题。

- 改了指标口径，就把 `METRICS_VERSION` 加 1，在 `$RETRO_DIR/ledger/tune-log.md` 写明前后不能直接比较，必要时重跑基线。
- 技能保持简短，只写判断依据和边界。

评估结论和调整方案并进 weekly-retro 第 6 步的确认表（单列一组「复盘本身」），和本期发现一起给用户逐条确认。没有要调整的也写一行结论。

做完评估就在 `$RETRO_DIR/ledger/tune-log.md` 追加一条，标题写成 `## <日期>（<年>-W<周> 评估）`，`tune_due.py` 靠这个标题算下次到期；
用户驳回全部调整也要记。

## 3. 落地（用户确认后）

- 改完后自测：`scan.py` 跑最近一周，`replay.py` 跑一两道题，hook 规则用最近一周的 Bash 命令回放。确认都能跑通、结果合理。
- 提交到你的技能仓库。
- 在这次评估的 `tune-log.md` 条目里补上：依据（哪几期、哪些证据）、改了什么、下次怎么判断这次调整有没有用。
